01

The change

Start with the capability, not the technology.

The project is being assessed against one core change request: enable historical analysis of Queensland traffic events and make useful patterns quickly explorable in a web interface.

The review deliberately separates the business need from implementation choices. A pipeline, database, web framework or deployment method may support the change, but none of those technologies are the requirement by themselves.

Review approach

The technical prototype already existed. This case study applies a structured BA review to formalise the need, test the scope, establish traceability and identify what still requires verification before further development.

Current state & gap

The problem is not access to live traffic information. It is retaining and analysing it over time.

The current-state review compares what is already available with the capability needed for historical analysis. The important gaps are persistent collection and storage, programmatic analysis, and a clear way to expose selected results.

Scope discipline

The existing prototype includes notifications. During requirements refinement that capability is being reassessed because it does not directly support the current core change request. It is not being used to justify the primary business outcome simply because it already exists.

04

Requirements

Eight requirements currently define the working scope.

The matrix is still a working artefact: all verification and validation fields remain open. The summary below keeps the case study readable while the full traceability matrix is available as supporting evidence.

R-001Historical retention

Use case: The Data Analyst can access traffic events from the previous 30 days after they are no longer available from the live source.

Acceptance: Unique events remain queryable across a continuous 30-day period after disappearing from the source.

R-002Automated collection

Use case: The system collects traffic-event information without manual intervention.

Acceptance: New traffic-event observations are collected automatically at the agreed interval throughout the collection period.

R-003Event identity vs observations

Use case: The Data Analyst can count and compare events without repeated observations being counted as separate incidents.

Acceptance: Repeated observations with the same source event identifier remain associated with one event while state changes can still be retained.

R-004Queryable historical analysis

Use case: The Data Analyst can analyse traffic events by time, suburb or location, and event type.

Acceptance: Stored data can be filtered or grouped across those dimensions and return consistent counts.

R-005Public metrics

Use case: A public viewer can quickly understand selected traffic patterns through the website.

Acceptance: Selected metrics are presented in plain language without requiring access to the underlying dataset.

R-006Time since last crash

Use case: A public viewer can see how long it has been since the most recent selected traffic event.

Acceptance: Elapsed time is calculated from the latest qualifying stored event and presented in a human-readable form.

R-007Analysis-ready data

Use case: The Data Analyst can obtain retained data in a structure suitable for further analysis.

Acceptance: Historical records can be retrieved as consistent tabular data without manual restructuring.

R-008Collection completeness

Use case: The analyst can determine when historical data may be incomplete because collection failed.

Acceptance: Failed collection periods are identifiable and cannot silently appear as valid zero-event periods.

From requirements to delivery

Trace the requirement to an existing capability, then prove it.

This is retrospective traceability, not a claim that every requirement existed before the first line of code. The purpose is to identify what the existing prototype already supports, what evidence exists, and what still has to be tested.
